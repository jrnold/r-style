# Evidence for r-code-style rules

Checked 2026-10-29 against the live pages below, converted to Markdown and
searched for each rule's wording. Quotes are verbatim, trimmed with `...`.
Rules marked † in `SKILL.md` have no published tidyverse source and are house
rules. Re-check with the repository's `check-upstream` skill.

Sources:

- **Style**: tidyverse style guide, <https://style.tidyverse.org/>
  (`syntax`, `functions`, `pipes`, `ggplot2`, `errors`, `tests`).
- **Design**: Tidy design principles, <https://design.tidyverse.org/>.
- **R Packages**: Wickham and Bryan, 2nd ed., <https://r-pkgs.org/>.
- **Advanced R**: Wickham, 2nd ed., <https://adv-r.hadley.nz/>.
- **rlang / vctrs / testthat** reference docs and source on GitHub.

## Error messages

All from Style, [errors](https://style.tidyverse.org/errors.html).

  | Rule | Quote                                                                                                                                                                                                                                                  |
  | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | 24   | "Every error message should start with a general statement of the problem ... The problem statement should use sentence case and end with a full stop."                                                                                                |
  | 25   | "If the cause of the problem is clear (e.g. an incorrect type or size), use “must”" / "If you cannot state what was expected, use “can't”"                                                                                                             |
  | 26   | "use a bulleted list ... Use cross bullets (`x`) to let the user know what the problem is, then use info bullets (`i`) to provide contextual information." / "Try to keep the sentences short and sweet" / "Prefer the singular in problem statements" |
  | 27   | "If the source of the error is clear and common, you may want to provide a hint ... The hint should be the last bullet, use an info bullet (`i`), and end in a question mark."                                                                         |
  | 28 † | No source. The chapter's nearest advice is to avoid hints unless the problem is common, "because you want to avoid steering users in the wrong direction".                                                                                             |
  | 29   | "If you can detect multiple problems, list up to five." / "If the list of issues might be long, make sure to truncate to only show the first few"                                                                                                      |
